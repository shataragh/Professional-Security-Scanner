🔧 Core Execution Syntax

All commands are executed from the project root directory:

python3 professional-security-scanner.py [OPTIONS]

Required Argument

FlagDescription
-t, --targetTarget URL (must start with http:// or https://)

⚙️ Execution Profiles & Modes

1. Basic Assessment Mode (Default)

Non-intrusive vulnerability sweep. Uses stealth profile by default.

python3 professional-security-scanner.py -t http://target.com
  • Threads: 2 | Delay: 1.0s
  • Modules: Recon + Fingerprinting + Passive Discovery
  • Output: HTML/JSON reports only

2. Aggressive Mode (Recommended for Labs)

Balanced speed and depth. Enables all core scanning modules.

python3 professional-security-scanner.py -t http://target.com -p aggressive
  • Threads: 20 | Delay: 0.02s
  • Modules: All 34 modules (recon, injection, API, external tools, chains)
  • Includes: Nmap, Nikto, SQLMap, Nuclei, ffuf, httpx, dalfox, gau

3. Extreme Mode (Maximum Coverage)

Highest concurrency for time-sensitive engagements (CTFs, pentests).

python3 professional-security-scanner.py -t http://target.com -p extreme
  • Threads: 40 | Delay: 0.01s | Max Payloads: 5,000
  • Enables: Race condition testing, deep blind SQLi, parallel credential stuffing

4. Stealth Mode (Evasion-Focused)

Designed for real-world red team operations where detection must be minimized.

python3 professional-security-scanner.py -t http://target.com -p stealth --self-protect
  • Threads: 2 | Delay: 1.0s
  • Human-like timing jitter (±30%)
  • Randomized User-Agent rotation
  • Realistic HTTP headers (Sec-Fetch-*, Accept-Encoding, etc.)
  • Circuit breaker (pauses after 15 failures)
  • Proxy rotation (if --proxies provided)

🛡️ Self-Protection System (Optional Flags)

These flags activate operational security features. They are disabled by default to maximize speed in lab environments.

FlagPurposeEffect
--self-protectEnable evasion logicAdds UA rotation, timing jitter, circuit breaker
--proxies <file>Load proxy listRotates IPs on block (format: ip:port or user:pass@ip:port)
--hydraEnable brute-forceActivates Hydra against discovered login forms
--user <username>Custom username for HydraDefaults to admin
--wordlist <path>Custom password wordlistOverrides default SecLists paths

Example: Full Stealth + Brute-Force

python3 professional-security-scanner.py \
  -t https://prod-api.example.com \
  -p stealth \
  --self-protect \
  --proxies /root/proxies.txt \
  --hydra \
  --user admin
💡 Tip: For local lab testing, omit --self-protect to get maximum speed and debug visibility.

🧠 Intelligence Engine: How Findings Are Validated

Before any attack chain executes, every finding passes through the Intelligence Engine, which performs 5-layer validation:

Layer 1: Honeypot Detection

  • Checks for canary tokens (x-canary, canary, decoy)
  • Detects decoy endpoints (e.g., /admin returning perfect 200 with 100KB response)
  • Flags tracking parameters (_cb=, session_id=, utm_*)

Layer 2: False Positive Filtering

  • Filters generic errors (error, exception, invalid)
  • Skips default pages (welcome, index, placeholder)
  • Rejects CAPTCHA-only responses

Layer 3: Cross-Reference Validation

  • Requires corroboration from ≥2 tools (e.g., LFI found by both custom scanner and ffuf)
  • Rejects single-tool detections unless confidence > 90%

Layer 4: Behavioral Analysis

  • Detects suspicious response times (<0.1s or >30s)
  • Flags "perfect" responses (large size + 200 status on sensitive paths)

Layer 5: Contextual Validation

  • Verifies target consistency (e.g., no localhost in remote scan)
  • Ensures technology stack matches findings (e.g., no WordPress CVE if WP not detected)

Output Indicators

Console TagMeaning
🚨 HONEYPOT DETECTEDHigh-confidence honeypot; do not exploit
⚠️ FALSE POSITIVE LIKELYLow-confidence finding; manual review recommended
✅ HIGH CONFIDENCEReady for attack chaining
❌ CROSS-REFERENCE FAILEDIsolated finding; requires verification

Findings with confidence < 60% are excluded from attack chains but remain in reports.

📤 Output & Reporting

All results are saved to --output (default: /tmp/scan_results).

├── report.html          # Interactive dashboard (color-coded severity)
├── report.json          # Machine-readable (includes confidence, chains, context)
├── scanner.log          # Full terminal log (debugging/auditing)
├── scan_state.pkl       # Resume point (for --resume)
├── nuclei_results.json  # Raw Nuclei output
├── ffuf_results.json    # Raw ffuf output
├── httpx_results.json   # Raw httpx output
└── ...

Report Highlights

  • HTML Dashboard: Shows Attack Context (credentials, hashes, versions), Protection Status, and Chain Execution Results.
  • JSON Schema: Includes target, self-protection status, findings array, performance metrics, context summary, and attack chain execution logs.
